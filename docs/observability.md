# Request correlation, logs and metrics

Stiff provides opt-in application logs and a native server metrics snapshot. No
collector, background logging service or public metrics endpoint is installed.
The [example app](../examples/app.bend) enables logs and exposes `GET /metrics`
behind its synthetic demonstration gate. Production access policy belongs to the
application; that gate is not authentication.

## Correlation and structured logs

Wrap the application handler with `App.observe(next, request)`. Each normally
returning invocation writes one JSON line to stderr before transport submission:

```json
{"event":"handler_result","request_id":"12","method":"GET","proposed_status":200,"active":true,"duration_ms":3}
```

The returned reply gets `X-Request-Id` using `Incoming.id`. IDs are generated by
the server, unique during its single listener lifetime, and restart from one in
a new process. They are not globally unique, random, authentication capabilities,
or distributed tracing IDs. An inbound `X-Request-Id` is not adopted. The observer
replaces an inner handler's same-name response header; trusted outer middleware
can still modify a reply. Use deployment/process metadata when combining logs.

Fields have deliberately narrow meanings:

- `proposed_status` is the handler's returned status, before transport validation
  or subsequent outer middleware. It does not establish delivery to the client.
- `active` is the request's cooperative activity check when the handler returns.
  A timeout during later logging or writing can still close the request.
- `duration_ms` measures the next handler using the pinned runtime's monotonic
  millisecond clock. It excludes socket acceptance, request-body reading, this
  log's encoding/output and response transmission.

Place this wrapper outside application gates/routing to see application errors
as well as successful results, and use it once to avoid duplicate records.
Paths, query strings, headers, request/response bodies and error messages are not
logged. This avoids copying credential-bearing or unbounded request data into
access logs; applications needing route labels should use their own bounded,
trusted labels. JSON encoding failure emits a fixed `log_encoding_failed` line.

A handler that never returns has no result log. Earlier parser rejection,
connection admission and pending/handler overload rejection also have no such
log or observer-generated response ID. Use native counters for the covered
transport outcomes. Logs use the pinned runtime's synchronous stderr output on Bend's execution
path. Sink backpressure can delay application work; the runtime treats a failed
standard-stream write as fatal. Stiff adds no unbounded log queue, sink-failure
isolation or durable/exactly-once recording. Use a reliable, drained sink when
enabling this wrapper; these records are not an audit journal.

## Native metrics

`Web.Server.metrics()` returns `IO(Web.Metrics)`. `Web.metrics_json(snapshot)`
converts the snapshot to a JSON value suitable for `Web.json_value` or a private
exporter. It works before listening (zeros) and after shutdown. There is no reset
API and no implicit network exporter.

| Field | Meaning |
| --- | --- |
| `admitted` | Fully read requests accepted into the application queue |
| `completed` | Admitted responses whose libevent write-completion callback ran |
| `failed` | Subset of completed responses with status 400–599 |
| `rejected` | Errors sent by Stiff before admission, including overload; an attempted error response, not proof of delivery |
| `expired` | Admitted requests closed by their network deadline or shutdown grace |
| `read_expired` | Accepted sockets whose absolute pre-dispatch read timer fired |
| `disconnected` | Admitted requests cleaned up after libevent reported a connection close, before completion |
| `connections` | Current accepted connection contexts, including incomplete requests and pending cleanup |
| `pending` | Current admitted network requests |
| `handlers` | Current reserved queued/claimed handler budgets, including expired handlers that have not finished |

Libevent can reject malformed protocol data before Stiff's admission callback;
those rejections are not covered by `rejected`. Kernel-backlog clients and
connection attempts are not counted. A disconnected client may be discovered
only on later I/O; if the deadline closes it first, it counts as `expired`.
Completion means local transport completion, not that the remote application
consumed or committed the response.

The first seven fields are cumulative U32 counters, saturating at 4,294,967,295.
The final three are bounded current gauges. Fields are independently sampled
with atomic reads; a live snapshot is not a transaction and accounting identities
may briefly disagree while operations finish. Compare exact totals after work
has settled. An HTTP metrics request counts itself among admitted work and live
gauges. Reading metrics after network shutdown can still show outstanding Bend
handlers until they finish.

There are no per-path labels, percentiles, byte/CPU budgets, persistence or metric
histories. [Load measurements](benchmark.md) separately collect latency and RSS.
The native test suite checks compiled Metrics layout, correlation against response
headers, rejection before admission, completed error responses, late handler
results, read expiry, and gauges returning to zero after network and handler
cleanup. Normal and diagnostic sanitizer profiles exercise the same journeys.
